# 01 需求：用户、目标、范围与成功标准

## 用户与场景

内容团队的排期运营。每天要把一批素材排进各渠道（抖音 / B 站 / 微博）的发布时段。痛点有三个：
- 素材元数据经常缺字段；
- 文案里的风险词、版权状态需要逐条核对；
- 时段经常被其他团队占用，人工来回确认容易漏，甚至重复排期。

## 目标

给定一批 `素材 ID + 渠道 + 期望发布时间 + 时间是否硬性`，Agent 要做到以下几点：
1. 读取素材并按审核规则检查，给出审核状态和风险原因；
2. 查询时段，在无冲突的前提下给出建议时段；
3. 把可以排的素材保存为**排期草稿**（只是草稿，不发布）；
4. 列出所有需要人确认的事项，并如实返回每条草稿的保存状态。

## 输入

| 字段 | 说明 |
|---|---|
| `material_id` | 素材 ID，对应 `data/materials.json` |
| `channel` | `douyin` / `bilibili` / `weibo` |
| `requested_slot` | 期望时段 `YYYY-MM-DD HH:00`，可为 null（表示信息缺失） |
| `time_requirement` | `flexible`：可以建议替代时段；`hard`：不得擅自改期 |

## 输出（每项素材）

审核状态、风险原因、要求时段、建议时段、待确认项、草稿状态（`saved` / `not_saved` / `save_failed`）、草稿 ID、决策依据；另有整体任务状态（`completed` / `needs_user_action` / `failed` / `incomplete`）。

## 范围

**包含**：审核规则检查（必填字段、绝对化用语、音乐版权及补查、促销信息、渠道时长）、时段冲突处理（已有排期、同批其他草稿）、草稿保存与幂等、故障注入、步数上限，以及 CLI 运行和 Trace 输出。

**不包含**：真实发布、真实业务系统对接、UI、多 Agent、并发写锁、多日排期优化。

## 成功标准（对应题目验收点）

| 验收点 | 成功标准 |
|---|---|
| 正常排期 | 审核通过、时段可用，保存草稿，状态 `completed` |
| 素材信息缺失 | 不排期，指出缺失字段 / 不存在 / 缺时间，要求补充 |
| 规则风险 | 阻断类不排期并给出原因；须确认类可存草稿，但标记待确认；版权待核实先补查再下结论 |
| 时段冲突 | 弹性时间：建议最近的可用时段，草稿标记待确认；硬性时间：不改期、不保存，请求确认 |
| 重复提交 | 同一请求运行两次只有一份草稿；改时段后重提交时更新原草稿，不新建 |
| 保存失败 | 明确返回 `save_failed`，任务状态 `failed`，不得声称成功 |
| 通用 | 任何输出都不出现"已发布"；达到步数或调用上限时返回 `incomplete` |

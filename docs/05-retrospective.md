## 最难的问题

**哪些交给模型决定，哪些必须由代码保证？**

题目同时要求"模型动态决策"和"不能越权、不能虚报"。如果把规则全写进提示词，模型确实能自主决策，但它出错就是关键缺陷；如果全写成 if/else，安全了，却不算 ReAct。

最终的划分是：
- **模型负责选择**：先查什么、要不要补查、选哪个替代时段、保存还是请求确认、失败后是否重试、何时结束。
- **代码负责底线**：没有发布工具；`save_draft` 内置护栏（冲突、硬性时间、阻断素材、缺时间、改时段必须待确认）；`submit_result` 与工具账本对账，不一致就打回，最后以事实覆盖。

真实运行证明这个划分是必要的。同样的输入，模型第一次没给缺时间的素材保存草稿，第二次却自选时段保存了。如果只靠提示词，这个问题就会时有时无。加了护栏以后，模型撞到护栏会收到明确的错误，然后自己调整（03、07 的路径 C）。护栏本身也成了"观察 → 调整"的信号来源。

## 学习收获

1. **一定要看真实模型的 Trace。** Mock 和单元测试都通过的时候，两个问题都还没暴露：无状态的规则检查让模型反复补查；护栏漏掉了 null 要求时间。它们只在读真实 Trace 时才出现。
2. **工具返回要能指导下一步。** `check_rules` 返回 `needs_lookup`，模型就知道该补查；补查完如果仍返回旧状态，模型就会困惑、重复调用。工具设计的对象其实是模型这个"用户"，返回值必须反映它已经做过的动作。
3. **幂等键要从业务语义出发。** 最初想用请求 ID 做幂等，但"更换时段后重新提交"会生成第二份草稿。改用 `(素材, 渠道)` 作为键，同一份草稿原地更新版本，两个验收点就同时满足了。
4. **用让 `reason` 成为必填参数的方式留下决策依据**，不需要模型暴露内部思维过程，Trace 也能逐步说明它为什么这么做。

## 下一步

- 对每个用例在真实模型上做多次采样（如 10 次），统计各验收点的通过率，量化决策的稳定性。
- 草稿库换成 SQLite，并为 `(material_id, channel)` 加唯一约束，解决并发写的问题。
- 支持断点续跑：根据工具账本恢复已完成的步骤，只处理剩余素材。
- 增加用户确认回路：用户回复"同意改到 19:00"后，把草稿从 `pending_confirmation` 转为 `draft`，硬性时间也可以在用户明确授权后改期。
- 排期推荐考虑跨日时段，以及渠道流量和优先级。
